# FleetPi: real Pi agents on Glimmer four-bit

FleetPi + Fleet completed all three website updates **3.03× faster** than the matched eight-agent vLLM-Metal baseline in this trial. Both passed every round and all 251 final checks. This is an end-to-end system comparison, not an attribution of the gain to the Pi extension alone.

The single agent missed rounds 1 and 2, then recovered to a passing final site in round 3. It generated substantially less output by merging work after those misses. Its elapsed time is **not a comparable time-to-success for the staged workflow**, so no single-agent speedup is claimed. The first missing call was traced to malformed ATEM generated by the model; the exact raw response and replay are preserved.

## Conditions and interpretation

- Mac M5 Pro, 48 GB unified memory; identical cached Muse Glimmer 30B MLX affine four-bit weights (group size 64).
- Eight page fragments, three released stakeholder rounds, protected browser checks at mobile and desktop sizes. Actual Pi read/edit/write/ls/check_site tools, sessions and token-based compaction.
- All modes: 96K context tokens, 4,096 output tokens/response, 40 turns/agent/round, one runner repair pass, two checker permits. No output truncation or compaction occurred in the primary trials.
- Default vLLM performance settings: native caching/batching retained. Both vLLM arms use the same isolated Glimmer attention correction and source-guarded streaming handoff plugin; the global installation is untouched.
- Fleet: Metal/NAX four-bit kernels, exact n-gram drafting (k15), shared-prefix coalescing, hardware-aware admission and per-agent ready repairs. No learned DFlash drafter, approximate SPAN, layer skipping or activation sparsity.
- Same task facts/tools/acceptance conditions; enhanced common context is placed in the system prompt, baseline facts in the first user message. This intentionally tests the integrated harness and engine, not identical token streams or an engine-only ablation.
- Fresh sessions and one engine at a time. Task wall excludes engine load and initial screenshot setup, and includes tools, checks, retries and any compaction. Output rate is API-reported output/task wall, including reasoning; it is not GPU decode speed.
- Darwin physical footprint is sampled at 1 Hz, including charged GPU memory. Engine-only and whole-pipeline peaks are in summary.json. Provider cache counters are not assumed comparable across backends.
- One primary trial per mode; no significance or general 8× claim. The original successful stock-parser vLLM8 run is retained as historical evidence. The externally stopped debug single attempt is excluded.
- The frozen v1 `passed` field means final cumulative score. This report separately requires all staged milestones for workflow success; current harness code makes that distinction explicit. Raw evidence is unchanged.

## Reproduce

In a fresh checkout, use the frozen patch to reconstruct the measured harness rather than its later reliability fixes:

```sh
python3 integrations/fleetpi/bootstrap.py --patch results/fleetpi/frozen/fleetpi-trial.patch
python3 integrations/fleetpi/configure.py
make -j6 BUILD=build-fleetpi build-fleetpi/fleet-serve
npm ci --prefix demos/site-refactor
node integrations/fleetpi/scripts/compare.mjs results/fleetpi/new-comparison
```

The fixture, model revision, source/binary hashes and exact flags are frozen in the protocol/configs. Numerical variation and asynchronous scheduling can change generated text and timing. The current default FleetPi build adds atomic resume state, immutable attempt/check evidence, cancellation cleanup, stale-verification invalidation and explicit attempt/cumulative accounting; these were tested after the timed trials.
